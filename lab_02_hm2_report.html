1. Problem and Approach

1.1 Task Description

The objective of this laboratory exercise is to construct, validate, and test a responsive Android data capture form that incorporates structured user input verification, explicit confirmation dialogs, configuration change resilience (screen rotation), and responsive UX considerations (small displays, large accessibility text, and on-screen soft keyboard visibility). The system captures mandatory fields, single-choice selections, and optional annotations, validating them before presenting a modal summary with dual Confirm and Edit / Cancel paths.

1.2 Assumptions

  • Field Structure:
    • Name: Required alphanumeric text; cannot be blank.
    • Email: Required RFC-compliant email string checked via Android's Patterns.EMAIL_ADDRESS regex.
    • Date of Birth: Required date selected via embedded DatePicker; must represent a historical date (not in the future).
    • Work Status: Single-choice selection driven by a dynamic Spinner backed by an ArrayAdapter.
    • Comments / Notes: Explicitly optional multiline field that may remain empty without halting form submission.
    • Terms Agreement: Mandatory boolean CheckBox required prior to finalizing draft review.
  • Data Ownership vs. Committal: The form activity owns the in-memory draft state until the user explicitly executes the "Confirm" action. Cancellation must guarantee zero side-effects and retain all entered values for user correction.

1.3 Intended System Behaviour

  1. Responsive Presentation: The form is hosted within a vertical ScrollView container to prevent layout clipping and afford fluid vertical scrolling when software keyboards (IME) occupy the viewport.
  2. Strict Pre-Confirmation Validation: When the user triggers submission, fields are checked sequentially. If any requirement fails, validation halts, visual error indicators (setError()) and focus highlights are assigned to the offending widget, and actionable Toast warnings are emitted.
  3. Non-Destructive Review: A modal AlertDialog summarizes valid inputs. Selecting Edit / Cancel dismisses the dialog with 100% preservation of all widget values. Selecting Confirm triggers official committal and navigation to the preview screen.
  4. Configuration Resilience: Rotating the device between portrait and landscape preserves all entered draft text, calendar settings, and spinner selections through Android's instance state bundles.

2. Design and Reasoning

2.1 Event Flow Architecture

The following event trace illustrates the end-to-end execution path from the user's click interaction through multi-tier validation, modal confirmation, and dual resolution branches:

EVENT TRACE: BUTTON CLICK → VALIDATION → CONFIRMATION → RESOLUTION

[ User taps "Submit" Button / Menu Item ]
    ↓
[ DataInput.handleSubmitAndConfirm() ]
    ↓
[ TIER 1: Validate Name (strName.isEmpty()?) ]
    ┌── YES → nameInput.setError(), nameInput.requestFocus(), Toast → [HALT]
    └── NO → Proceed to Tier 2
    ↓
[ TIER 2: Validate Email (Patterns.EMAIL_ADDRESS.matcher()) ]
    ┌── INVALID → emailInput.setError(), emailInput.requestFocus(), Toast → [HALT]
    └── VALID → Proceed to Tier 3
    ↓
[ TIER 3: Validate Date of Birth (chosenDate.after(today)?) ]
    ┌── FUTURE DATE → Toast warning → [HALT]
    └── VALID PAST → Proceed to Tier 4
    ↓
[ TIER 4: Validate Terms Checkbox (agreeTerms.isChecked()?) ]
    ┌── UNCHECKED → Toast warning → [HALT]
    └── CHECKED → Validation Complete!
    ↓
[ Extract Optional Comments + Single-Choice Spinner Status ]
    ↓
[ Build and Display AlertDialog Summary ("Confirm Submission") ]
    ┌── [User taps "Edit / Cancel"] → Dialog dismissed; all widget inputs retained [NO COMMIT]
    └── [User taps "Confirm"] → commitRecord() → Intent launched → DisplayActivity [COMMITTED]

2.2 Displaying a Dialog vs. Committing a Record

A fundamental architectural principle demonstrated in this lab is the distinction between displaying a confirmation dialog and committing a record:

  • Displaying a Dialog (Transient Presentation): A modal AlertDialog is an ephemeral user interface component rendered on the window manager layer. It merely mirrors the current state of local view memory for human verification. Displaying the dialog does not mutate application storage, trigger database insertions, issue network requests, or modify persistent state. If the process is killed or the user cancels, the dialog vanishes without side effects.
  • Committing a Record (State Transition): Committal is the permanent or transactional acceptance of verified data. It transitions the data from an editable draft into persistent storage (e.g., Room database, SharedPreferences, REST API backend, or cross-activity navigation payload). Committal only occurs when the user explicitly triggers the positive confirmation listener (setPositiveButton("Confirm", ...)).

2.3 Responsive Layout & Accessibility Remediation

To satisfy diverse mobile form factors, the layout was architected with the following considerations:

  • Scroll Container Justification: Wrapping the vertical input hierarchy in a root ScrollView with android:fillViewport="true" ensures that when users focus text inputs and the software keyboard (IME) slides up on small screens (e.g., 4.7" devices or split-screen mode), form controls remain fully scrollable without being occluded.
  • Accessible Labels vs. Placeholders: Floating hints and placeholders often disappear or cause confusion once typing begins. Explicit, permanent bold TextView labels were placed directly above each input field.
  • Accessibility Remediation:
    • Identified Issue: Standard input fields often lack explicit programmatic associations, causing Android TalkBack screen readers to announce generic labels like "Editing text" without contextual guidance. Furthermore, lack of autofill hints degrades accessibility for motor-impaired users.
    • Correction Applied: Integrated explicit android:autofillHints (e.g., name, emailAddress) and paired permanent visible labels. Ensured touch targets across the Spinner, CheckBox, and Button satisfy the WCAG minimum recommendation of 48dp height/width.

2.4 Conceptual Analysis & Question Responses

1. Why must validation happen before confirmation?
  • Integrity and User Trust: Presenting an unvalidated summary implies to the user that their inputs are acceptable. Showing a confirmation dialog with invalid data (e.g., malformed email or missing name), only to reject it after the user clicks "Confirm", degrades user trust and creates cognitive friction.
  • Resource Efficiency: Formatting summary strings, calculating calendar bounds, and constructing modal dialog hierarchies consumes memory and window manager allocations. Validating early (failing fast) avoids unnecessary UI allocations.
  • Security and Defensive Design: Strict pre-confirmation validation ensures that downstream consumers (dialog builders, database serializers, network payloads) receive sanitized, non-null, and type-safe data.
2. Which component owns the draft, and when may it be cleared?
  • Draft Ownership: The current foreground Activity (DataInput) and its associated view hierarchy own the draft state in local memory. During configuration changes (rotation), ownership is temporarily held by the Android framework via the onSaveInstanceState(Bundle) mechanism.
  • When Draft May Be Cleared:
    1. Upon Successful Committal: Only after the user confirms submission and the record is safely persisted or handed off to the destination activity.
    2. Explicit User Reset: When the user deliberately chooses the "Clear Form" action from the options menu.
    3. Never on Edit/Cancel: Dismissing or cancelling the confirmation dialog must never clear the draft; the user must be returned to their populated form for easy editing.
3. What evidence shows that cancelling did not commit anything?
  • Retained View State: Upon tapping "Edit / Cancel", the dialog dismisses and the user observes all entered data (name, email, selected date, spinner position, comments, checkbox) exactly as entered, proving no form destruction occurred.
  • Zero State-Changing Invocations: Inspecting the negative button callback reveals: 
    .setNegativeButton("Edit / Cancel", (dialog, which) -> {
    popupToast("Submission cancelled. Values retained for editing.");
})
    No call to commitRecord(), no startActivity() intent invocation, and no repository write operations exist in this execution path.
  • Back Stack Invariance: The navigation stack remains unchanged; no new task records or activity instances are pushed onto the back stack.

3.2 Validation & Confirmation Handler (DataInput.java)

private void handleSubmitAndConfirm() {
    EditText nameInput = findViewById(R.id.editTextName);
    EditText emailInput = findViewById(R.id.editTextEmail);
    DatePicker dobInput = findViewById(R.id.DatePickerDOB);
    Spinner sp = findViewById(R.id.spinner);
    EditText commentsInput = findViewById(R.id.editTextComments);
    CheckBox agreeTerms = findViewById(R.id.chkAgreeTerms);

    // 1. Validation: Name (required, non-empty)
    String strName = nameInput.getText().toString().trim();
    if (strName.isEmpty()) {
        nameInput.setError("Name is required");
        nameInput.requestFocus();
        popupToast("Validation failed: Please enter a name");
        return;
    }

    // 2. Validation: Email (required, valid email pattern)
    String strEmail = emailInput.getText().toString().trim();
    if (strEmail.isEmpty()) {
        emailInput.setError("Email is required");
        emailInput.requestFocus();
        popupToast("Validation failed: Please enter an email address");
        return;
    } else if (!Patterns.EMAIL_ADDRESS.matcher(strEmail).matches()) {
        emailInput.setError("Enter a valid email address (e.g. name@domain.com)");
        emailInput.requestFocus();
        popupToast("Validation failed: Invalid email format");
        return;
    }

    // 3. Validation: Date of Birth (must not be in the future)
    Calendar chosenDate = Calendar.getInstance();
    chosenDate.set(dobInput.getYear(), dobInput.getMonth(), dobInput.getDayOfMonth());
    Calendar today = Calendar.getInstance();
    if (chosenDate.after(today)) {
        popupToast("Validation failed: Date of birth cannot be in the future");
        return;
    }

    // 4. Validation: Mandatory Terms Checkbox
    if (!agreeTerms.isChecked()) {
        popupToast("Validation failed: Please agree with the terms and conditions");
        return;
    }

    // Extract single-choice spinner and optional comments
    int row = sp.getSelectedItemPosition();
    String strStatus = (row >= 0 && row < status.length) ? status[row] : "Unknown";
    String strDOB = dobInput.getDayOfMonth() + "/" + (dobInput.getMonth() + 1) + "/" + dobInput.getYear();
    String strComments = commentsInput.getText().toString().trim();
    if (strComments.isEmpty()) {
        strComments = "(None provided)";
    }

    String readableSummary = "FORM SUMMARY\n"
            + "------------------------\n"
            + "Name: " + strName + "\n"
            + "Email: " + strEmail + "\n"
            + "DOB: " + strDOB + "\n"
            + "Work Status: " + strStatus + "\n"
            + "Comments: " + strComments + "\n"
            + "Terms Agreed: Yes";

    // Show Confirmation AlertDialog with Confirm and Edit/Cancel behaviour
    new AlertDialog.Builder(this)
            .setTitle("Confirm Submission")
            .setMessage(readableSummary)
            .setPositiveButton("Confirm", (dialog, which) -> {
                commitRecord(readableSummary);
            })
            .setNegativeButton("Edit / Cancel", (dialog, which) -> {
                popupToast("Submission cancelled. Values retained for editing.");
            })
            .show();
}

3.3 Instance State Preservation Across Configuration Changes (Rotation)

@Override
protected void onSaveInstanceState(@NonNull Bundle outState) {
    super.onSaveInstanceState(outState);
    EditText nameInput = findViewById(R.id.editTextName);
    EditText emailInput = findViewById(R.id.editTextEmail);
    EditText commentsInput = findViewById(R.id.editTextComments);
    DatePicker dobInput = findViewById(R.id.DatePickerDOB);
    Spinner sp = findViewById(R.id.spinner);
    CheckBox agreeTerms = findViewById(R.id.chkAgreeTerms);

    outState.putString(KEY_NAME, nameInput.getText().toString());
    outState.putString(KEY_EMAIL, emailInput.getText().toString());
    outState.putString(KEY_COMMENTS, commentsInput.getText().toString());
    outState.putInt(KEY_YEAR, dobInput.getYear());
    outState.putInt(KEY_MONTH, dobInput.getMonth());
    outState.putInt(KEY_DAY, dobInput.getDayOfMonth());
    outState.putInt(KEY_SPINNER_POS, sp.getSelectedItemPosition());
    outState.putBoolean(KEY_TERMS, agreeTerms.isChecked());
}

@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    // ... layout inflation ...
    DatePicker dp = findViewById(R.id.DatePickerDOB);
    if (savedInstanceState != null) {
        int y = savedInstanceState.getInt(KEY_YEAR, 2004);
        int m = savedInstanceState.getInt(KEY_MONTH, 1);
        int d = savedInstanceState.getInt(KEY_DAY, 13);
        dp.init(y, m, d, null);
    } else {
        dp.init(2004, 1, 13, null);
    }
    // Spinner restore
    if (savedInstanceState != null) {
        sp.setSelection(savedInstanceState.getInt(KEY_SPINNER_POS, 0));
    }
}
