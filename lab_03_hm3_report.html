1. Problem and Approach

1.1 Task Description

The objective of this laboratory exercise is to design, implement, and analyze an Android application options menu integrated with interactive navigation and responsive user feedback mechanisms. The system connects XML menu resource definitions with Java activity lifecycle callbacks (onCreateOptionsMenu and onOptionsItemSelected), dispatches user interactions to dedicated handlers, executes state-changing screen transitions, and provides appropriate, proportionate user feedback via transient Toasts and modal Alert Dialogs.

1.2 Assumptions

  • Application Architecture: The application follows single-task activity stacks where DataInput acts as the primary data entry interface, and DisplayActivity serves as the secondary detail/preview screen.
  • Feedback Categorization: Transient, non-critical confirmations (such as resetting form fields or initiating an exit) are communicated using Toast widgets. In contrast, critical validations (missing mandatory terms acceptance) or dense record inspection require modal dialogs or explicit activity navigation to prevent data loss and ensure user awareness.
  • Stable References: Menu selection handling must strictly rely on permanent Android resource IDs (R.id.*) declared in XML rather than displayed string titles, guaranteeing runtime localization independence.

1.3 Intended System Behaviour

  1. Menu Display: The options menu attaches to the app bar on launch, presenting at least three functional items (Next, View Records, Clear Form, About, and Exit).
  2. Validation & Modal Inspection: Tapping Next validates the required Terms agreement checkbox; if invalid, feedback is provided; if valid, an AlertDialog summarizes the inputs with options to either dismiss or navigate.
  3. Screen Transition: Tapping View Records gathers the current state and navigates via an explicit Intent to DisplayActivity.
  4. Safe State & Back Stack: Pressing the system Back button from the secondary screen returns the user safely to the pristine input form without triggering duplicate transactions or saving operations.
  5. Unhandled Item Safety: Unrecognized or system-generated menu IDs safely delegate to super.onOptionsItemSelected(item).

2. Design and Reasoning

2.1 Menu Architecture and Lifecycle Attachment

In Android, the options menu lifecycle is decoupled into declaration (XML), inflation (Activity initialization), and dispatch (event handling).

EVENT FLOW & LIFECYCLE DISPATCH

[ User taps Overflow / Action Bar Menu ]
    ↓
[ Activity.onCreateOptionsMenu(Menu menu) ]
    ↓ (MenuInflater.inflate(R.menu.data_input, menu))
[ Menu XML parsed & MenuItems inflated into Action Bar ]
    ↓
[ User taps specific MenuItem ]
    ↓
[ Activity.onOptionsItemSelected(MenuItem item) ]
    ↓
[ item.getItemId() evaluation via switch/if-else ]
    ┌── R.id.itemNext → displayNextAlert() [Validation + Modal Alert / Screen Transition]
    ┌── R.id.itemViewRecords → handleViewRecords() [Explicit Intent → DisplayActivity]
    ┌── R.id.itemClear → handleClearForm() [Reset Fields + Toast Feedback]
    ┌── R.id.itemAbout → handleAbout() [Informational AlertDialog]
    ┌── R.id.itemExit → popupToast() [Non-critical Toast Warning]
    └── default → return super.onOptionsItemSelected(item) [Safe System Fallback]

2.3 Navigation and Back Stack Dynamics

When View Records is selected, an explicit Intent is instantiated: 

Intent intent = new Intent(this, DisplayActivity.class);
intent.putExtra(DisplayActivity.EXTRA_DISPLAY_TEXT, content);
startActivity(intent);

Event Path and Idempotent Back Stack:

  • startActivity(intent) pushes a new DisplayActivity instance onto the task's Back Stack. DataInput transitions through onPause() to onStop(), preserving its existing view hierarchy and state in memory.
  • When the user presses the system Back button (or gesture), Android invokes finish() on DisplayActivity, popping it off the stack and destroying it.
  • DataInput returns to the foreground through onRestart() → onStart() → onResume(). Crucially, returning via the Back stack does not trigger form submission callbacks, menu clicks, or network writes, preventing duplicate accidental records.

2.4 Conceptual Analysis & Question Responses

1. Why should code use a menu item ID rather than the displayed label?
  • Internationalization and Localization (i18n/l10n): Display labels change across locales (e.g., "Next" in English, "Suivant" in French, "Agiliza" in Swahili). If business logic checked item.getTitle().equals("Next"), changing device language breaks all conditional logic. Resource IDs (e.g., R.id.itemNext) are compile-time integer constants that remain identical regardless of locale.
  • UI Refactoring & Typography: Copywriters frequently tweak UI text (e.g., changing "Next" to "Continue" or "Proceed"). Tying code to strings creates tight coupling. IDs provide strict decoupling of presentation from logic.
  • Performance: Comparing primitive integers (int id == R.id.itemNext) requires a single CPU cycle, whereas string matching involves string allocations and character-by-character equality checks.
2. When is a Toast unsuitable feedback?
  • Critical Validation Errors / Unsaved Work: Toasts disappear automatically after 2 to 3.5 seconds (LENGTH_SHORT or LENGTH_LONG) without requiring user acknowledgement. If a user looks away, they will miss why their submission failed. A modal AlertDialog or inline error label (setError()) is required.
  • Actionable Feedback (Needing User Input or Undo): Toasts are strictly non-interactive and cannot host clickable buttons or affordances. For actions requiring an immediate "Undo" (e.g., deleting a file), a Snackbar is appropriate.
  • Accessibility (Screen Readers): Toasts do not receive input focus and can be easily missed or interrupted by screen readers like TalkBack, making them poor for visually impaired accessibility.
  • Sensitive or Confidential Information: Toasts render at the window manager level above all apps; displaying account balances, passwords, or personal identity numbers in Toasts risks shoulder-surfing and security exposure.
3. What prevents menu recreation or rotation from repeating a save?
  • Decoupling Callbacks from Lifecycle: Configuration changes (such as screen rotation) trigger activity destruction and recreation (onDestroy() → onCreate() → onCreateOptionsMenu()). However, onCreateOptionsMenu() only prepares and inflates the menu structure; it does not execute onOptionsItemSelected().
  • Explicit User Intent Requirement: onOptionsItemSelected() is an asynchronous input event listener dispatched exclusively when a hardware or touch tap event is detected on a specific item. Because lifecycle recreation does not synthesize user input events, save operations are never repeated merely by recreating the menu.
  • Architecture Best Practices: Critical data operations should be mediated by ViewModels and repository layers using transactional state flags or SingleLiveEvent / Flow patterns, ensuring orientation changes do not re-emit execution triggers.

3.2 Menu Inflation & Safe Dispatching (DataInput.java)

@Override
public boolean onCreateOptionsMenu(Menu menu) {
    // Inflate the menu resource into the screen's action bar
    getMenuInflater().inflate(R.menu.data_input, menu);
    return true;
}

@Override
public boolean onOptionsItemSelected(MenuItem item) {
    // Dispatch based on stable compiled resource ID
    int id = item.getItemId();
    if (id == R.id.itemNext) {
        displayNextAlert();
        return true;
    } else if (id == R.id.itemViewRecords) {
        handleViewRecords();
        return true;
    } else if (id == R.id.itemClear) {
        handleClearForm();
        return true;
    } else if (id == R.id.itemAbout) {
        handleAbout();
        return true;
    } else if (id == R.id.itemExit) {
        popupToast("You want to exit why not just start another application");
        return true;
    } else {
        // Safe fallback for unhandled or system-level IDs
        return super.onOptionsItemSelected(item);
    }
}

3.3 Action Handlers & Navigation

private void handleViewRecords() {
    EditText nameInput = findViewById(R.id.editTextName);
    DatePicker dobInput = findViewById(R.id.DatePickerDOB);
    EditText emailInput = findViewById(R.id.editTextEmail);
    Spinner sp = findViewById(R.id.spinner);

    String strName = nameInput.getText().toString();
    String strDOB = dobInput.getDayOfMonth() + "/" + (dobInput.getMonth() + 1) + "/" + dobInput.getYear();
    String strEmail = emailInput.getText().toString();
    int row = sp.getSelectedItemPosition();
    String strStatus = (row >= 0 && row < status.length) ? status[row] : "Unknown";

    String summaryText = "CURRENT RECORD PREVIEW\n"
            + "-------------------------\n"
            + "Name: " + (strName.isEmpty() ? "(No name entered)" : strName) + "\n"
            + "DOB: " + strDOB + "\n"
            + "Email: " + (strEmail.isEmpty() ? "(No email entered)" : strEmail) + "\n"
            + "Work Status: " + strStatus;

    // Transition to secondary activity
    navigateToDisplayActivity(summaryText);
}

private void handleClearForm() {
    ((EditText) findViewById(R.id.editTextName)).setText("");
    ((EditText) findViewById(R.id.editTextEmail)).setText("");
    ((DatePicker) findViewById(R.id.DatePickerDOB)).updateDate(2004, 1, 13);
    ((Spinner) findViewById(R.id.spinner)).setSelection(0);
    ((CheckBox) findViewById(R.id.chkAgreeTerms)).setChecked(false);

    popupToast("Form inputs reset successfully");
}

private void handleAbout() {
    new AlertDialog.Builder(this)
            .setTitle("About FormInputExample")
            .setMessage("FormInputExample v1.0\nICS 2300 Mobile Application Development\nDemonstrating Options Menu, Navigation, Dialogs and Toast feedback.")
            .setPositiveButton("OK", null)
            .show();
}

4. Fault Diagnosis and Correction Record

In accordance with task requirement 4, a deliberate fault was introduced, triaged, diagnosed, and resolved.

Stage Observation & Diagnostic Details
Introduced Fault In DataInput.java, the ID lookup in onOptionsItemSelected was deliberately altered to check an incorrect ID (e.g., checking id == R.id.itemAbout instead of R.id.itemViewRecords, or mistyping the XML item identifier to @+id/itemViewRecord).
Observed Symptom When the user tapped "View Records" from the options menu, the screen did not change, no activity transition took place, and the application fell through to the default branch with complete silence.
Root Cause The MenuItem.getItemId() returned the valid inflated ID R.id.itemViewRecords, but the conditional branching failed to match any explicit branch, delegating immediately to super.onOptionsItemSelected(item) which returned false.
Correction Applied Synchronized the XML declaration <item android:id="@+id/itemViewRecords" ... /> with the Java switch condition:
else if (id == R.id.itemViewRecords) { handleViewRecords(); return true; }.
Retest & Verification Rebuilt application (gradle assembleDebug), redeployed, and triggered "View Records". The DisplayActivity launched instantly with current record details.
